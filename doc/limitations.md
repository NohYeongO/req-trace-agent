# 한계와 향후 개선

## 설계상 선택한 한계
| 한계 | 이유 | 보완 |
|---|---|---|
| AI는 구현 여부를 **판정하지 않는다** | 코드만 보고 판정하면 틀렸을 때 검수 문서가 오염된다. 이전 접근에서 실측 정확도는 0.5 수준이었다 | 사실의 출처는 개발자 보고로 둔다. 근거(파일·API·커밋·PR)는 Git에 실제로 있는지만 확인해 표시한다 |
| 사람 확인 전에는 아무것도 저장하지 않는다 | 매핑 완전 일치율이 0.727이다. 틀린 제안이 그대로 쌓이면 진척률이 틀린다 | 확인 화면에서 요구사항과 조건을 체크박스로 고친다 |
| 수치는 LLM이 만들지 않는다 | 작은 모델은 숫자 해석(가장 낮은 분류, 우선순위 등)을 자주 틀렸다 | 수치와 본문은 코드가 만들고, LLM 문장은 코드가 대조한 뒤 틀리면 재작성하거나 빼거나 대체한다 |

## 현재 한계
- **매핑 재현율 0.926**
  - 한 보고에 요구사항이 4개 이상 섞이면 뒤쪽을 놓친다.
  - 확인 화면에서 직접 추가할 수 있지만, 사람이 놓치면 진척률이 낮게 잡힌다.
- **근거 확인은 '존재' 확인까지만 한다**
  - 파일, 엔드포인트, 커밋, PR이 있는지만 본다.
  - 그 코드가 조건을 실제로 만족하는지는 테스트 결과 보고서의 요구사항별 테스트 연결로 간접 확인할 뿐이다.
- **개발 명세서는 Spring(JPA·`@RestController`)과 DDL만 지원한다**
  - 파서가 정규식 기반이다. 복잡한 상속, 제네릭 응답 래퍼, Kotlin, MyBatis XML은 놓칠 수 있다.
- **출력은 docx와 xlsx뿐이다**
  - 공공 기관이 요구하는 HWP는 직접 만들지 못한다. 한글 프로그램에서 docx를 열어 변환해야 한다.
- **응답 시간**
  - 로컬 qwen3:8b 기준으로 코멘트가 있는 채팅은 약 7초, 개발 명세서는 약 90초가 걸린다. 대부분 LLM 생성 시간이다.
  - 서버 기동 후 첫 요청은 임베딩 모델 로딩으로 3초 더 걸린다.
- **추적 데이터의 외부 전송**
  - LangSmith는 외부 SaaS라서 켜면 입력과 출력이 외부로 나간다.
  - 공공 사업 내부망에서는 꺼야 한다(`LANGCHAIN_TRACING_V2=false`). 대신 화면의 단계별 진행 이벤트(SSE)와 평가 스크립트로 확인한다.
- **단일 사업, 단일 사용자**
  - 업무 DB가 SQLite 파일 하나다. 로그인, 권한, 여러 사업 분리가 없다.

## 향후 개선
1. **산출물 종류 확장**
   - 사용자 매뉴얼, UAT 시나리오와 결과, 인수인계서, 성능과 보안 점검 요약.
   - 산출물 레지스트리에 모듈 하나(양식, 수집 도구, 작성, 검증 함수)를 추가하면 같은 흐름을 탄다.
2. **매핑 재현율 개선**
   - 보고를 요구사항 단위 문장으로 먼저 나눈 뒤 매핑한다.
   - 사람이 고친 확인 결과를 few-shot 예시로 쌓아 다시 쓴다.
3. **근거와 테스트 연결 강화**
   - 근거로 적힌 파일을 실제로 거치는 테스트를 JaCoCo 라인 단위로 찾는다.
   - 그 테스트가 통과했는지까지 근거에 표시한다.
4. **내부망 운영**
   - LangSmith 대신 자체 호스팅 추적(Langfuse 등)이나 로컬 로그 기반 추적을 쓴다.
   - HWP 변환 연동(한컴 변환 서버)도 필요하다.
5. **응답 속도**
   - 서버 기동 시 임베딩과 MCP 도구를 미리 불러 콜드스타트를 없앤다.
   - 논리명 추정은 여러 테이블을 한 번에 묶어 LLM 호출 횟수를 줄인다.
6. **다중 사업과 권한**
   - 사업별 DB 분리, PM·개발자·검수자 역할 구분.
