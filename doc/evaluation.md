# 평가

모든 평가는 같은 입력으로 다시 돌릴 수 있게 스크립트와 결과 파일을 저장소에 둔다.
- 모델: 로컬 Ollama `qwen3:0.6b`(라우팅), `qwen3:8b`(작성), `bge-m3`(검색 임베딩)
- 데모 데이터: 커머스 프로젝트 zerofive-store. 요구사항 32건, 완료 조건 63개, 완료 보고 11건, 기준일 2026-03-10

| 평가 | 스크립트 | 결과 파일 |
|---|---|---|
| 완료 보고 → 요구사항 매핑 | `eval/run_intake_eval.py` | `eval/results/intake-*.json` |
| 현황 채팅 | `eval/run_chat_eval.py` (`data/eval/chat_cases.json` 24문항) | `eval/results/chat/*.json` |
| 산출물 초안 | `eval/run_deliverable_eval.py` | `eval/results/deliverables/*.json` |

## 1. 완료 보고 → 요구사항 매핑
데모 보고 11건을 정리 그래프에 넣는다. 사람 확인 단계에 올라온 AI 제안을 담당자 정답(`data/demo/reports.json`의 `expected`)과 비교한다.

| 지표 | qwen3:8b + bge-m3 | fake 백엔드(규칙 + 해시 임베딩) |
|---|---|---|
| 요구사항 정밀도 | **1.000** | 0.781 |
| 요구사항 재현율 | **0.926** | 0.926 |
| 완료 조건 정밀도 | **0.979** | 0.792 |
| 완료 조건 재현율 | **0.939** | 0.857 |
| 완전 일치(보고 단위) | **0.727** (8/11) | 0.273 |
| 매핑 재시도 | 0회 | 6회 |
| 보고당 소요 | 14.6초 | 0.5초 |

- **틀린 3건**
  - 한 보고에 요구사항 4개가 섞인 경우, 뒤쪽 2개(SFR-013, SFR-004)를 놓쳤다.
  - 조건 하나를 빠뜨린 경우가 있었다(SFR-012).
  - 이미 충족된 조건(QUR-003 #62)을 다시 넣은 경우가 있었다.
- 틀린 3건 모두 **사람 확인 화면에서 체크박스로 고칠 수 있는 범위**다. 저장 전에 담당자가 확정한다.
- 이전 데모(petclinic, 보고 19건)에서도 비슷한 수준이었다: 요구사항 P 0.955 / R 0.955, 조건 P 0.974 / R 0.927 (`eval/results/petclinic/`).

## 2. 현황 채팅 — 개선 전/후 (같은 24문항)
문항마다 답에 반드시 있어야 할 사실(`must`)과 있으면 안 되는 표현(`forbid`, 묻지 않은 전체 수치·다른 대상)을 정해 두고 채점한다.

문항 유형:
- 요구사항 하나
- 분류별, 전체, 미완료, 위험
- 담당자, 기간("지난주", "최근 7일")
- 이름 검색("장바구니")
- 후속 질문("그럼 품질은?", "남은 조건이 뭐야?")

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| 정답률 | 58.3% (14/24) | **100%** (24/24) |
| 라우팅 정확도 | 95.8% | **100%** |
| 사실 재현율 | 0.794 | **1.000** |
| 묻지 않은 정보가 섞인 답 | 4건 | **0건** |
| 부자연스러운 표현(마크다운 강조 등) | 52개 | **0개** |
| 평균 응답 시간 | 6.9초 | **1.0초** |

- **개선 전 구조:** LLM이 MCP 결과 전체를 받아 답 전체를 썼다.
- **개선 전 오류:** 이름 검색(장바구니, 쿠폰), 기간, 담당자, 후속 질문에서 틀렸다. 정답 문항에도 묻지 않은 전체 수치가 섞였다.
- **개선 내용:**
  1. 질문 분석(대상, 기간, 분류, 후속 질문 맥락)과 답의 본문을 **코드**가 만든다.
  2. LLM은 해석이 필요할 때만 한두 문장 코멘트를 쓴다.
  3. 코멘트 속 숫자, ID, 주장(우선순위, 가장 낮은 분류 등)은 코드가 다시 확인한다. 틀리면 다시 쓰게 하고, 끝내 틀리면 코멘트를 뺀다.
- **응답 시간이 준 이유:** 코멘트가 필요 없는 질문은 LLM을 부르지 않는다.
- **재현:**
  - 개선 전 결과: `eval/results/chat/baseline-ollama-20261021-103217.json`
  - 현재 평가 세트로 다시 채점: `python eval/run_chat_eval.py --rescore <파일>`

## 3. 산출물 초안
산출물에서 AI가 맡는 작업은 두 가지다.
- **테스트 결과 보고서:** 서술 섹션(종합 의견, 실패 원인 요약). 문장 속 숫자와 테스트명은 결과 파일에서 계산한 사실과 대조한다.
- **개발 명세서:** 테이블과 컬럼, 인터페이스의 한글 논리명 추정. 용어 사전에 없는 것만 대상이고, 한글이나 약어 형식인지, 길이는 적절한지 검사한다.

검증에서 반려되면 사유를 붙여 그 작업만 다시 쓴다(최대 2회). 끝내 틀리면 코드 문장이나 '미정'으로 대체한다.

| 문서 | 입력 | AI 작업 | 1차 통과 | 재작성 | 대체 | 수치 경고 | 소요 |
|---|---|---|---|---|---|---|---|
| 테스트 결과 보고서 | 1차 결과(2026-03-09, 실패 포함) | 서술 2 | 2 | 0 | 0 | 0 | 16.7초 |
| 테스트 결과 보고서 | 2차 결과(2026-03-10, JaCoCo 포함) | 서술 1 | 1 | 0 | 0 | 0 | 6.7초 |
| 개발 명세서 | zerofive-store main | 논리명 추정 14 | 14 | 0 | 0 | 0 | 95.8초 |
| **합계** | | **17** | **17 (100%)** | **0** | **0** | **0** | |

- 수치 경고는 저장된 문서 서술에서 결과 자료에 없는 숫자나 고유번호가 나온 섹션 수다. 0이어야 한다.
- 결과 자료에서 계산한 값은 AI가 바꿀 수 없다: 통과율, 실패 묶음, 커버리지, 엔티티와 DDL의 불일치.
- 개발 명세서는 엔티티와 DDL 교차 분석에서 불일치 10건을 찾아 '엔티티와 DDL 불일치' 절에 표시했다. 10건 모두 NULL 허용 여부 차이다.
  - 엔티티는 NOT NULL인데 DDL은 NULL 허용: 8건(`coupon.discount_amount`, `event.threshold` 등)
  - DDL은 NOT NULL인데 엔티티 연관은 NULL 허용: 2건(`order_items.order_id`, `order_session_items.order_session_id`)
- 결과 파일: `eval/results/deliverables/deliverables-ollama-20261022-085649.json`

## 4. 지연 분석 (LangSmith)
LangSmith 트레이스로 노드별 시간을 확인했다. 트레이스 이름은 그래프별로 붙인다: `chat`, `report_intake`, `report_confirm`, `criteria_draft`, `deliverable:*`.

| 흐름 | 전체 | 구성 |
|---|---|---|
| 채팅(코멘트 있음) | 7.6초 | 라우팅 qwen3:0.6b 0.9초, MCP 3회 0.1초 미만, **코멘트 qwen3:8b 6.4초(84%)** |
| 완료 보고 정리 | 6.7초 | 추출, RAG 검색, 매핑 LLM이 대부분 |
| 개발 명세서 | 91.5초 | 논리명 추정 LLM 호출 14회가 대부분. 소스 분석은 1초 미만 |

- 서버 기동 후 첫 요청만 느리다. 첫 MCP 도구 탐색에 0.2초, 첫 검색에서 임베딩 모델 로딩에 3초가 걸린다. 이후는 캐시되어 0.02초다.
- 응답 시간을 더 줄이려면 코드 처리보다 **LLM 호출 횟수와 출력 길이**를 줄여야 한다.
